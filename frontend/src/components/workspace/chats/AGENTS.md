### Fork-specific frontend notes

Rationale and the tests that pin each of these live in [FORK.md](../../../../../FORK.md).

- **Live chat slots (fork feature)** keep the chat you are looking at, plus any chat still answering after you left it, mounted above the route. The single live chat was extracted from `[thread_id]/page.tsx` into `src/components/workspace/chats/chat-instance.tsx` — a **fully controlled** component (its owner owns `threadId`/`isNewThread`; it reports new→real promotion via `onThreadStarted`) that wraps its own provider stack (`chat-providers.tsx`, with a per-instance `storageScope` so several artifacts panels do not collide on one pathname). `src/components/workspace/chats/keep-alive-chat-viewport.tsx` is mounted **above the route** in `workspace-content.tsx` and renders one `<ChatInstance>` per slot (the current chat + the background ones), displaying only the active one (`display:none` on the rest keeps them mounted, preserves scroll, and keeps streams running). `src/core/threads/live-chat-slots.ts` is the pure, unit-tested model (retain/release/promote); `live-chat-slots-context.tsx` owns the background set + active-slot key. **Nothing here is persisted and there is no tab strip** — a background slot exists only for the run it is finishing and is released by the provider's effect once that run leaves `busyKeys`, which runs _after_ the stream's own `onFinish` so releasing never pre-empts the "conversation finished" notification. The user-managed strip this replaced (pin/close/reorder, `localStorage` + `GET`/`PUT /api/settings/chat-tabs`) was removed once sidebar folders shipped: filing a chat is the durable way to keep it to hand, and a pinned strip was a second, competing place to do it. In app builds `[thread_id]/page.tsx` is a thin **registrar** (reports the route to `syncRoute`, renders nothing); in static-demo builds the feature is off and the page renders the classic inline `<ChatInstance>`. Because the new→real rewrite uses `history.replaceState` (not the Next router), `syncRoute` matches the current slot by its **stable key**, never by the mutable thread id, so re-reporting a just-promoted new chat cannot clobber it. `ChatBox` derives its resizable-panel ids from the thread id (not the pathname) so co-mounted instances never collide. Pinned by `tests/unit/core/threads/live-chat-slots.test.ts` and `tests/unit/core/threads/live-chat-slots-busy.dom.test.tsx`.
- **Concurrent chats (fork feature)** rest on two things that look optional and are not. Every `thread.submit` in `core/threads/hooks.ts` must send `onDisconnect: "continue"`: the Gateway's default is `"cancel"`, so without it leaving a chat kills its run — and the SDK's own default is derived from `streamResumable`, which `sanitizeRunStreamOptions` strips before the request, so it cannot be relied on. Rejoining a surviving run is the existing `reconnectOnMount` path. Second, `ChatInstance` reports `reportBusy(slotKey, thread.isLoading)` (via `useMaybeLiveChatSlots`, null outside the viewport) and `syncRoute` **retains the slot it is leaving while that slot is busy**, reusing its key so the mounted instance is not torn down. Do not retain a slot that is still `isNew` (a background slot is addressed by a real thread id) and do not evict one to make room — a full set declines, and the run still survives server-side. Returning to a retained chat **adopts** its instance rather than mounting a second on the same thread, and the slot is released once the run leaves `busyKeys` — from an effect, so it never pre-empts `onFinish`'s notification. Pinned by `tests/unit/core/threads/run-disconnect.test.ts`, `live-chat-slots-busy.dom.test.tsx`, and `tests/e2e/concurrent-chats.spec.ts`.
- `src/components/workspace/chats/chat-box.tsx` owns the desktop right-panel layout, and **all three** right panels (artifacts, sidecar, browser) share one `ResizablePanelGroup` — do not fork a non-resizable branch per panel kind, which is how the artifacts divider silently lost its drag handle (#4465). Open/close is `collapse()` / `resize()` on the side panel's imperative handle, not conditional rendering, so the width can animate. Three constraints hold that together: the size transition is applied from the group as `[&>[data-panel]]:transition-[flex-grow]` because the sized flex item is the library's own `[data-panel]` element rather than the child `className` lands on; it is applied only while an open/close is in flight, so a drag is not interpolated frame by frame; and during the animation the panel content is held at its final width in `cqw` and clipped, because a reflowing message list re-runs its scroll-to-bottom (pinned by `tests/e2e/sidecar-chat.spec.ts`'s no-animated-scroll test) and a re-wrapping composer changes which responsive labels it shows. Because the panel is `collapsible`, the library can also collapse it to `0%` on its own when a drag crosses `minSize`, without going through the state that owns it. `onResize` records the last positive size while the pointer moves, but the owning `sidecar` / `browserView` / `artifactsOpen` state must only mirror a final `0%` layout from `onLayoutChanged`, after pointer release; closing on the first `0%` resize frame breaks a continuous drag that reaches the edge and then reverses before release.
- **Democracy panels (fork feature)** are launched from a dialog under _New chat_, never from the composer's mode dropdown — a panel means nothing without a roster, and the dialog is the only place the cost can be shown _before_ it is spent. Three things are load-bearing. `core/threads/run-context.ts::deriveModeContext` is the single derivation of the booleans the backend actually reads (`mode` itself is inert server-side); it replaced two copies at the submit and regenerate call sites in `core/threads/hooks.ts` that could disagree, so keep it one function. It must send `max_total_subagents` for a panel: the run-wide ledger defaults to 6, a three-model panel needs 6 for its happy path alone, and `task` calls past the ledger are discarded with their work lost — omit it and the panel is silently truncated mid-run. And the setup-to-chat handoff (`core/threads/democracy.ts` stash + `DEMOCRACY_LAUNCH_EVENT`, claimed in `chats/use-democracy-launch.ts`) needs **both** the mount path and the event listener: launching from a chat that is already `/workspace/chats/new` is a same-route `router.push`, which remounts nothing, so a mount-only effect makes the button do nothing at all. The claimed task must reach the composer as `InputBox`'s **`initialValue`**, never through `setInput` — the textarea is uncontrolled and the draft-hydration effect runs after mount and overwrites anything written during it, a bug that is invisible when the launch arrives by event (after hydration) and silent when it arrives on mount, which is now the normal path. Attachments ride a module-level carrier rather than the localStorage stash because a `File` does not survive `JSON.stringify` and setup has no thread to upload against yet.
- **The composer's internet switch (fork feature)** is per conversation, so it is a `THREAD_SCOPED_CONTEXT_KEYS` entry in `core/settings/local.ts`, never a shared `LocalSettings` section like the memory toggle — taking one chat offline must not unplug the others. Default **on**: `undefined` is not `false`, so a chat that predates it keeps its tools. Both submit paths in `core/threads/hooks.ts` send `resolveInternetEnabled(context)` explicitly rather than letting the `...context` spread carry it, and that helper normalizes to a strict boolean because the backend opts out on `false` alone — a stringy `"false"` would read as _enabled_. The control publishes `data-slot="internet-toggle"` for specs to find it by.
- **Auto rename (fork feature)** is the chat header's `ThreadAutoRename`, and its shape is deliberate in both directions. `POST /api/threads/{id}/title/suggest` only **reads** — it returns a title and `core/threads/auto-rename.ts` applies it by delegating to `useRenameThread`. Writing the title on the suggest route as well would put the "409 while a run is in flight" rule in a second place that does not hold `reserve_checkpoint_write`; re-implementing the rename instead of delegating would give the cache dance (cancel pending snapshot reads **before** writing the title in, or a list response that started earlier restores the old name) a second copy that stops matching. The picker is the shared `ModelSelect` and the pick is stored in the **same** `autoTitle.modelName` key Settings → Conversation titles uses, so the two screens cannot disagree about which model runs; a stored name no longer in `config.yaml` falls back to _Server default_ rather than preselecting one the Gateway answers with a 400. The dialog's selection is **derived**, not an effect — an effect keyed on `models` resets the pick on every render, because `useModels()` hands back a fresh array whenever its query has no data. What the backend feeds the model is the narrow part (FORK.md §38): tool results carry an Ultra turn's entire subagent deliberation, so they are dropped, and the answer for a turn is the last AI message with text. Pinned by `tests/unit/core/threads/auto-rename.test.ts`, `tests/unit/components/workspace/thread-auto-rename.dom.test.tsx` and `tests/e2e/auto-rename.spec.ts`.
