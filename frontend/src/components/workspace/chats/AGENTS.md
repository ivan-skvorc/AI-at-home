### Fork-specific frontend notes

Rationale and the tests that pin each of these live in [FORK.md](../../../../../FORK.md).

- **Keep-alive chat tabs (fork feature)** are a browser-style tab strip whose pinned chats stay mounted and live across navigation. The single live chat was extracted from `[thread_id]/page.tsx` into `src/components/workspace/chats/chat-instance.tsx` — a **fully controlled** component (its owner owns `threadId`/`isNewThread`; it reports new→real promotion via `onThreadStarted`) that wraps its own provider stack (`chat-providers.tsx`, with a per-instance `storageScope` so several artifacts panels do not collide on one pathname). `src/components/workspace/chats/keep-alive-chat-viewport.tsx` is mounted **above the route** in `workspace-content.tsx` and renders one `<ChatInstance>` per slot (pinned tabs + the current unpinned chat), displaying only the active one (`display:none` on the rest keeps them mounted, preserves scroll, and keeps streams running). `src/core/threads/chat-tabs.ts` is the pure, unit-tested model (pin/close/reorder/promote, local-cache serialization, DnD MIME types); `chat-tabs-context.tsx` owns the pinned set + active-slot key. **The pinned set is persisted server-side per user** via `core/threads/chat-tabs-api.ts` (`GET`/`PUT /api/settings/chat-tabs`), with `localStorage` (`deerflow.chat-tabs.<userId>`) demoted to a first-paint cache — it is per-browser _and_ per-origin, so on its own the set was lost to a site-data clear, storage eviction on an insecure origin, or reopening the app on a different origin (`localhost` vs. a LAN/Tailscale address). Reconciliation rules that must not regress: `fetchChatTabs` returns `null` for "unknown" (distinct from `[]` = "no tabs"), so an **unreachable gateway keeps the local cache** rather than blanking the strip — the normal state right after a machine restart, when the browser reopens the app before the backend is up; a server with **no** stored set adopts the local one and seeds the server (the upgrade path for tabs pinned before this existed); writes back are debounced and flushed on teardown/`pagehide`; and the local cache never writes an empty set over a stored one unless a user action produced it (mutations mark the key dirty), because on the gateway-offline boot the provider starts on the `…anonymous` key and the hydrate/persist effects run in the same commit. Pinned by `tests/unit/core/threads/chat-tabs-persistence.dom.test.tsx`. The strip itself (`chat-tabs-bar.tsx`) is the drop target and **must stay rendered as an empty drop zone when there are no tabs yet** (showing the `chatTabs.dropHint` hint whenever the thread list is non-empty) — collapsing it to `null` leaves a new-chat user with nowhere to drag onto, which is the whole feature; it hides only when there is nothing to drag (no history) and, with the rest of the viewport, on non-chat pages. In app builds `[thread_id]/page.tsx` is a thin **registrar** (reports the route to `syncRoute`, renders nothing); in static-demo builds the feature is off and the page renders the classic inline `<ChatInstance>`. Because tab switches use `history.replaceState` (not the Next router — same reason as the chat page's new→real rewrite), `syncRoute` matches the current slot by its **stable key**, never by the mutable thread id, so re-reporting a just-promoted new chat cannot clobber it. `ChatBox` derives its resizable-panel ids from the thread id (not the pathname) so co-mounted instances never collide. Pinned by `tests/unit/core/threads/chat-tabs.test.ts` and `tests/e2e/chat-tabs.spec.ts`.
- **Concurrent chats (fork feature)** rest on two things that look optional and are not. Every `thread.submit` in `core/threads/hooks.ts` must send `onDisconnect: "continue"`: the Gateway's default is `"cancel"`, so without it leaving a chat kills its run — and the SDK's own default is derived from `streamResumable`, which `sanitizeRunStreamOptions` strips before the request, so it cannot be relied on. Rejoining a surviving run is the existing `reconnectOnMount` path. Second, `ChatInstance` reports `reportBusy(slotKey, thread.isLoading)` (via `useMaybeChatTabs`, null outside the viewport) and `syncRoute` **pins the slot it is leaving while that slot is busy**, reusing its key so the mounted instance is not torn down; the strip renders a `chat-tab-busy` dot for those keys. Do not pin a slot that is still `isNew` (a tab is addressed by a real thread id) and do not evict a tab to make room — a full strip declines, and the run still survives server-side. Pinned by `tests/unit/core/threads/run-disconnect.test.ts`, `chat-tabs-busy.dom.test.tsx`, and `tests/e2e/concurrent-chats.spec.ts`.
- `src/components/workspace/chats/chat-box.tsx` owns the desktop right-panel layout, and **all three** right panels (artifacts, sidecar, browser) share one `ResizablePanelGroup` — do not fork a non-resizable branch per panel kind, which is how the artifacts divider silently lost its drag handle (#4465). Open/close is `collapse()` / `resize()` on the side panel's imperative handle, not conditional rendering, so the width can animate. Three constraints hold that together: the size transition is applied from the group as `[&>[data-panel]]:transition-[flex-grow]` because the sized flex item is the library's own `[data-panel]` element rather than the child `className` lands on; it is applied only while an open/close is in flight, so a drag is not interpolated frame by frame; and during the animation the panel content is held at its final width in `cqw` and clipped, because a reflowing message list re-runs its scroll-to-bottom (pinned by `tests/e2e/sidecar-chat.spec.ts`'s no-animated-scroll test) and a re-wrapping composer changes which responsive labels it shows. Because the panel is `collapsible`, the library can also collapse it to `0%` on its own when a drag crosses `minSize`, without going through the state that owns it. `onResize` records the last positive size while the pointer moves, but the owning `sidecar` / `browserView` / `artifactsOpen` state must only mirror a final `0%` layout from `onLayoutChanged`, after pointer release; closing on the first `0%` resize frame breaks a continuous drag that reaches the edge and then reverses before release.
- **Democracy panels (fork feature)** are launched from a dialog under _New chat_, never from the composer's mode dropdown — a panel means nothing without a roster, and the dialog is the only place the cost can be shown _before_ it is spent. Three things are load-bearing. `core/threads/run-context.ts::deriveModeContext` is the single derivation of the booleans the backend actually reads (`mode` itself is inert server-side); it replaced two copies at the submit and regenerate call sites in `core/threads/hooks.ts` that could disagree, so keep it one function. It must send `max_total_subagents` for a panel: the run-wide ledger defaults to 6, a three-model panel needs 6 for its happy path alone, and `task` calls past the ledger are discarded with their work lost — omit it and the panel is silently truncated mid-run. And the setup-to-chat handoff (`core/threads/democracy.ts` stash + `DEMOCRACY_LAUNCH_EVENT`, claimed in `chats/use-democracy-launch.ts`) needs **both** the mount path and the event listener: launching from a chat that is already `/workspace/chats/new` is a same-route `router.push`, which remounts nothing, so a mount-only effect makes the button do nothing at all. The claimed task must reach the composer as `InputBox`'s **`initialValue`**, never through `setInput` — the textarea is uncontrolled and the draft-hydration effect runs after mount and overwrites anything written during it, a bug that is invisible when the launch arrives by event (after hydration) and silent when it arrives on mount, which is now the normal path. Attachments ride a module-level carrier rather than the localStorage stash because a `File` does not survive `JSON.stringify` and setup has no thread to upload against yet.
- **The composer's internet switch (fork feature)** is per conversation, so it is a `THREAD_SCOPED_CONTEXT_KEYS` entry in `core/settings/local.ts`, never a shared `LocalSettings` section like the memory toggle — taking one chat offline must not unplug the others. Default **on**: `undefined` is not `false`, so a chat that predates it keeps its tools. Both submit paths in `core/threads/hooks.ts` send `resolveInternetEnabled(context)` explicitly rather than letting the `...context` spread carry it, and that helper normalizes to a strict boolean because the backend opts out on `false` alone — a stringy `"false"` would read as _enabled_. The control publishes `data-slot="internet-toggle"` for specs to find it by.
